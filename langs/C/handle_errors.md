В языке C **нет исключений** (как в C++ или Python), поэтому «выбросить ошибку» в привычном смысле нельзя. Однако есть **стандартные и переносимые способы корректной обработки и диагностики ошибок**, которые позволяют понять **что пошло не так и где**.

Использовать просто `exit(1)` — **плохая практика**, потому что:
- Нет информации о **причине** ошибки,
- Нет информации о **месте** (файл, строка),
- Невозможно обработать ошибку на более высоком уровне (если это библиотека).

  ---

## ✅ Правильные подходы к обработке ошибок в C

### 1. **Вывод диагностического сообщения + `exit()` с кодом**
  Если программа — это **консольное приложение**, и ошибка критична (например, не удалось открыть файл), то:

```c
#include <stdio.h>
#include <stdlib.h>

int main() {
  FILE *f = fopen("config.txt", "r");
  if (!f) {
    fprintf(stderr, "Ошибка: не удалось открыть config.txt\n");
    exit(EXIT_FAILURE);  // лучше EXIT_FAILURE, чем 1
  }
  // ...
}
```

> ✅ Используйте `stderr` (а не `stdout`) для ошибок.  
> ✅ Используйте `EXIT_FAILURE` и `EXIT_SUCCESS` из `<stdlib.h>` — это переносимо.

---

### 2. **Добавьте информацию о месте ошибки: `__FILE__`, `__LINE__`**

```c
#define ERROR(msg) do { \
  fprintf(stderr, "Ошибка в %s:%d: %s\n", __FILE__, __LINE__, msg); \
  exit(EXIT_FAILURE); \
} while(0)

// Использование:
if (!ptr) ERROR("Не удалось выделить память");
```

Теперь вы увидите:
```
Ошибка в main.c:42: Не удалось выделить память
```

---

### 3. **Используйте `perror()` или `strerror(errno)` для системных ошибок**

Многие системные функции (`open`, `malloc`, `socket` и т.д.) устанавливают глобальную переменную `errno` при ошибке.

```c
#include <errno.h>
#include <string.h>

FILE *f = fopen("missing.txt", "r");
if (!f) {
  fprintf(stderr, "fopen: %s\n", strerror(errno));
  // или проще:
  perror("fopen");  // напечатает: "fopen: No such file or directory"
  exit(EXIT_FAILURE);
}
```

> 💡 `perror("fopen")` автоматически добавит имя функции и описание ошибки из `errno`.

---

### 4. **Для библиотек — не вызывайте `exit()`! Возвращайте коды ошибок**

Если вы пишете **библиотеку**, никогда не вызывайте `exit()` — это лишает вызывающий код контроля.

Вместо этого:
- Возвращайте **код ошибки** (например, `0` — успех, `-1` — ошибка),
  - Или используйте **out-параметр** для ошибки.

  Пример:
```c
// Возвращает 0 при успехе, -1 при ошибке
int load_config(const char *path, config_t *out) {
  FILE *f = fopen(path, "r");
  if (!f) {
    return -1; // вызывающий код сам решит, что делать
  }
  // ...
  return 0;
}

// В main:
if (load_config("app.conf", &cfg) != 0) {
  perror("load_config");
  exit(EXIT_FAILURE);
}
```

---

### 5. **(Опционально) Макросы для удобства**

Можно создать макрос вроде:

```c
#define DIE_ON_NULL(ptr, msg) do { \
  if ((ptr) == NULL) { \
    fprintf(stderr, "[%s:%d] ОШИБКА: %s: %s\n", \
        __FILE__, __LINE__, msg, strerror(errno)); \
    exit(EXIT_FAILURE); \
  } \
} while(0)

// Использование:
FILE *f = fopen("data.bin", "rb");
DIE_ON_NULL(f, "fopen failed");
```

---

### 6. **Коды возврата: что возвращать?**

| Значение | Значение |
|--------|--------|
| `0` | Успех (для `main` и утилит командной строки) |
| `EXIT_SUCCESS` | То же, что `0`, но выразительнее |
| `EXIT_FAILURE` | Общая ошибка (обычно `1`) |
| Конкретные коды (`1`, `2`, `3`...) | Для разных типов ошибок (редко, но бывает полезно) |

> 📌 В `main()` возврат `0` или `EXIT_SUCCESS` означает «всё хорошо» для оболочки (`$? == 0`).

---

## ❌ Чего НЕ делать

- ❌ `exit(1);` без пояснения — пользователь не поймёт, что случилось.
- ❌ Печатать ошибку в `stdout` — это мешает перенаправлению (`./app > result.txt`).
- ❌ Игнорировать `errno` после системных вызовов.
- ❌ Вызывать `exit()` из библиотечной функции.

---

## ✅ Итог

**Корректная обработка ошибок в C — это:**
1. Проверка возвращаемых значений,
2. Использование `errno` + `perror()`/`strerror()`,
3. Вывод сообщения в `stderr` с указанием **что**, **где** и **почему**,
4. Вызов `exit(EXIT_FAILURE)` **только в `main()` или в крайнем случае**,
5. В библиотеках — **возврат кодов ошибок**, а не аварийное завершение.

Такой подход делает программу **отлаживаемой, надёжной и дружелюбной к пользователю**.

В Linux для отправки и обработки **кастомных (пользовательских) сигналов** обычно используются два стандартных сигнала:  
- `SIGUSR1`  
- `SIGUSR2`

Эти сигналы **не имеют предопределённого назначения** и предоставляются разработчикам специально для реализации собственной логики межпроцессного взаимодействия .

---

### 🔧 Шаг 1: Обработка сигнала в C

Чтобы обработать сигнал, нужно зарегистрировать **обработчик (signal handler)** с помощью функции `signal()` или (предпочтительно) `sigaction()`.

#### Пример с `signal()`:

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <signal.h>

void handle_sigusr1(int sig) {
  write(STDOUT_FILENO, "Получен SIGUSR1!\n", 18);  // async-signal-safe
}

void handle_sigusr2(int sig) {
  write(STDOUT_FILENO, "Получен SIGUSR2!\n", 18);
}

int main() {
  signal(SIGUSR1, handle_sigusr1);
  signal(SIGUSR2, handle_sigusr2);

  printf("PID процесса: %d\n", getpid());
  printf("Отправьте сигнал: kill -SIGUSR1 %d\n", getpid());

  while (1) {
    pause(); // ждём любой сигнал
  }

  return 0;
}
```

> 💡 Используем `write()` вместо `printf()`, потому что `printf()` **не является async-signal-safe** и может привести к неопределённому поведению внутри обработчика.

---

### 📤 Шаг 2: Отправка сигнала

Есть несколько способов отправить сигнал:

#### 1. Из терминала:
```bash
kill -SIGUSR1 <PID>
# или
kill -USR1 <PID>
```

#### 2. Из другого C-процесса:
```c
#include <signal.h>
#include <sys/types.h>

kill(pid, SIGUSR1);  // pid — целевой процесс
```

#### 3. Самому себе (для теста):
```c
raise(SIGUSR1);  // эквивалентно kill(getpid(), SIGUSR1);
```

---

### 📌 Важные замечания

- `SIGUSR1` и `SIGUSR2` по умолчанию **завершают процесс**, если для них не установлен обработчик .
- Сигналы **не очередируются**: если отправить `SIGUSR1` 5 раз подряд, обработчик может вызваться только **один раз**.
- Для передачи данных вместе с сигналом можно использовать расширенный механизм `sigqueue()` и `sigaction()` с флагом `SA_SIGINFO`, но это сложнее и редко нужно для простых задач.

---

### ✅ Когда это полезно?

- Перезагрузка конфигурации демона по `SIGUSR1`.
- Включение/выключение отладочного режима по `SIGUSR2`.
- Простая координация между процессами без использования сокетов или файлов.

Таким образом, `SIGUSR1` и `SIGUSR2` — стандартный и переносимый способ реализовать **кастомное сигнальное взаимодействие** в Linux .

---

### 🔍 Почему всего два?

Сигналы — это **очень старый механизм IPC**, появившийся ещё в 1970-х. Их дизайн предполагает **минимализм и асинхронность**, а не передачу сложных сообщений. Поэтому:

- Сигналы — это **уведомления**, а не каналы данных.
- Они **не очередируются** (один и тот же сигнал может "сливаться").
- Их обработка должна быть **быстрой и безопасной** (ограниченный набор async-signal-safe функций).

Поэтому Unix-философия: **используй сигналы только для простых событий**, а для сложного обмена — другие IPC-механизмы.

---

### ✅ Что делать, если нужно больше "сигналов"?

#### 1. **Кодировать информацию внутри обработчика**
Используйте один сигнал (например, `SIGUSR1`), но **меняйте глобальное состояние** перед его отправкой:

```c
volatile sig_atomic_t command = 0;

void handler(int sig) {
  if (command == 1) {
    // перезагрузить конфиг
  } else if (command == 2) {
    // включить логгирование
  }
}

// Перед отправкой:
command = 2;
kill(pid, SIGUSR1);
```

⚠️ **Осторожно**: между записью в `command` и отправкой сигнала другой сигнал может прийти — возможна гонка. Но для простых случаев (например, один управляющий процесс) это работает.

---

#### 2. **Использовать `signalfd` (только Linux)**
Это **современный, надёжный способ** превратить сигналы в синхронные события:

- Блокируете сигналы с помощью `sigprocmask()`.
- Создаёте файловый дескриптор через `signalfd()`.
- Читаете из него структуры `signalfd_siginfo` — как из обычного сокета или pipe.
- Можно использовать в `select()`/`poll()`/`epoll`.

Преимущества:
- Сигналы **не прерывают выполнение**.
- Можно получать **множество сигналов** без потерь.
- Можно безопасно использовать обычные функции (нет ограничений async-signal-safe).

Но: это **не переносимо** (только Linux).

---

#### 3. **Использовать реальные IPC вместо сигналов**
Если вам нужно больше 2–3 типов сообщений — **сигналы, возможно, не лучший выбор**. Рассмотрите:

| Механизм        | Плюсы |
|------------------|------|
| **Unix-сокеты** (AF_UNIX) | Надёжные, очередируемые, передают данные |
| **Именованные каналы (FIFO)** | Просты, файлоподобны |
| **Очереди сообщений (POSIX или System V)** | Поддерживают типы сообщений |
| **Shared memory + семафоры** | Высокая производительность |

👉 **Сигналы — для уведомлений. IPC — для обмена.**

---

### 🧠 А есть вообще больше сигналов?

Да! В Linux доступно **около 30–60 сигналов** (зависит от архитектуры), но **большинство зарезервированы системой**:

- `SIGSEGV`, `SIGBUS` — ошибки памяти
- `SIGCHLD` — завершение дочернего процесса
- `SIGHUP` — разрыв терминала
- `SIGTERM`, `SIGKILL` — завершение

Некоторые из них **можно перехватывать и использовать**, но это **небезопасно и не рекомендуется**. Например, использование `SIGRTMIN`–`SIGRTMAX` — более правильный путь.

---

### ✅ Real-time сигналы: до 32+ "кастомных" сигналов!

Начиная с POSIX.1b, в Linux есть **real-time сигналы**:

```c
#define SIGRTMIN 34
#define SIGRTMAX 64  // на x86-64
```

Они:
- **Очередируются** (если отправить 5 раз — обработчик вызовется 5 раз),
  - Можно передавать данные через `sigqueue()`,
  - Предназначены именно для **пользовательских нужд**.

#### Пример:

```c
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

void handler(int sig, siginfo_t *info, void *context) {
  printf("Получен RT-сигнал %d, данные: %d\n", sig, info->si_value.sival_int);
}

int main() {
  struct sigaction sa = {0};
  sa.sa_sigaction = handler;
  sa.sa_flags = SA_SIGINFO;
  sigaction(SIGRTMIN, &sa, NULL);

  printf("PID: %d\n", getpid());
  pause();
}
```

Отправка из терминала **не поддерживается**, но из кода:

```c
union sigval val;
val.sival_int = 42;
sigqueue(pid, SIGRTMIN, &val);
```

Таким образом, у вас есть **до 30+ надёжных, очередируемых "кастомных" сигналов**!

---

### 🔚 Вывод

- Можно использовать **real-time сигналы** (`SIGRTMIN`–`SIGRTMAX`) — до 30+ штук, с очередями и данными.
- Или перейти на **настоящие IPC-механизмы**, если нужен обмен, а не просто уведомление.
- Сигналы — мощный, но **ограниченный** инструмент. Используйте их по назначению.
